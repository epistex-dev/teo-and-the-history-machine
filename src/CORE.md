# Core hooks and render contract

- `window.render_game_to_text()` is pure: it returns JSON and never changes game state.
- `window.advanceTime(ms)` steps the loop in 1/60 s frames. Fractions carry over between calls. Non-numbers, NaN and values <= 0 are ignored. One call advances at most `MAX_ADVANCE_MS` (30000 ms); larger values and Infinity are clamped to it.
- Deterministic stepping needs `?manual=1`: the real-time loop is stopped, `Date.now` is replaced by a virtual clock for the rest of the page's life, and only `advanceTime` moves time.
- Without `?manual=1` the real-time loop keeps running and `advanceTime` adds virtual frames on top of it, so frame counts are not reproducible. Every chapter test that asserts timing must use `?manual=1`.
- Chunk layout (`vite.config.ts`): `pz-<id>-<hash>.js` is the data of a puzzle, `chapter-<id>-<hash>.js` is its parsed script, `puzzle` (`src/puzzle/` plus the shared logic of `scripts/puzzles.mjs`) is the DOM puzzle player; a chapter loads only its own puzzle data and script. All are dynamic imports (`src/chapters.ts`); the first chapter's chunks are first load. `shell` (menu, settings, code, Sổ nguồn and log dialogs, loaded on the first click of `#menu-open`/`#log-open`), `screens` (card, timeline, final letter, loaded on first use) and `code` (`src/code.ts`, shared by those two) are lazy too, so the entry chunk stays under 50 000 characters (`tests/challenge/budget.spec.ts`); `assetsInlineLimit` is 0 for the same reason. `.size-limit.json` has a first-load entry and one per-chunk entry (150 kB gzip); the budget test fails when a `dist/assets/*.js` file matches no entry, so add an entry for each new chunk.
- Several `vite:preloadError` events can come from one failed load. `handleChunkFailure` reloads once and ignores the events that follow while the reload is pending. A failed `<link rel="modulepreload">` counts too: whether the browser re-fetches the module by itself is a race, and the reload must not depend on it. Only `beforeunload` (for 3 s) and a `pagehide` that is not going to the back/forward cache mark the page as leaving; a leaving page ignores chunk errors.

# Adding a chapter

1. `story/chapters/<id>.md` (front matter `id`, `title`; one `## <scene-id>` per scene; format and directives in `src/story/parse.ts` and `tests/fixtures/sample-chapter.md`). `<id>` must be in `ORDER` (`src/order.ts`). A chapter with a script plays; one without shows the "đang được viết" screen. After the last chapter (`ending`) the game goes to the end screen (`#end-screen`: Sổ nguồn, name card again, Chơi mới), never to a placeholder; it saves the scene `end` (`END_SCENE`, a scene id no chapter may use), so a refresh comes back to it; the `@code` beat shows the continue code on `#code-screen`, and in the last chapter that code is the finished one (see Shell, cards and codes). The parser rejects bad scripts at build time.
2. `story/puzzles/<id>.json` is the chapter's mini game: `loadPuzzle` (`src/chapters.ts`) plays it with `createPuzzleMinigame` in `src/puzzle/player.ts` (DOM, no canvas), the same player for every chapter. Components: `piece-board.ts` (bank and slots: assign, order, multi-capacity, mark), `evidence-board.ts` (cards), `conclusion.ts` (the ending's sentence). Bank order, the reply to a check and the help answer come from `virtual:puzzle-core` (`scripts/puzzle-core-plugin.ts`): the plugin cuts `bankOrder`, `model`, `reply`, `helpAnswer` and what they call out of `scripts/puzzles.mjs`, so the checker and the player cannot disagree and the solver and bots stay out of the bundle. Progress is saved per puzzle through the app's `SafeStorage` (`MinigameStart.storage`) under `teo:v1:puzzle:<id>` (placements, hint count, counts, pointed cards, conclusion fills) and removed on completion, by `Chơi mới` (every `teo:v1:puzzle:*` key) and by entering a code (the keys of the code's chapter and the chapters after it); a stored phase the file no longer has is dropped. `?preview=puzzle:<id>` opens any puzzle file for review through a storage wrapper that prefixes every key with `preview:`, so it never touches the real progress keys. `src/puzzle/slim.ts` cuts every puzzle file to the fields the player reads before it is bundled (`vite.config.ts`), so authoring notes, evidence quotes and hint fills never ship; piece ids in the DOM are opaque on the board (`pieceIds` in `scripts/puzzles.mjs`) and in the conclusion, never the file's ids or order; a conclusion piece's `url` may be a list and every address gets its own link. The puzzle contract (`story/puzzles/<id>.json`, `scripts/puzzles.mjs`) carries the no-fail rules of SPEC R4: hint tiers open one per press, nothing opens on idle, there is no ghost hand, and after 3 wrong checks the bar only offers the next tier. State goes through `describe()` (`MinigameHandle` in `src/minigame.ts`; `phase()` returns the puzzle phase, and the Menu's Sổ nguồn stays shut in the ending's `predict`, `demo` and `board` phases: one plain line says the cards are inside the machine as gears, and a Sổ nguồn already open when the board appears is closed by `onGears`); it ends up under `game` in `render_game_to_text()`. Sounds (place, remove, wrong check, hint, solve) go through `play()` in `src/audio.ts`, so mute, volume and the unlock rules apply. Rules and data: `story/puzzles/<id>.json`, the 25-row matrix in `story/minigames.json`.
3. Backdrops and props for a new chapter: a `@bg <id>` needs one row in `backdrops` of `src/story/stage-data.json` (colour, ground, `plate` id; an id missing there falls back to plain night), a room generator in `art/style/` registered in `ROOMS` (`assets.mjs`) that draws `bg-<plate>-portrait` and `-landscape`, and its placement in `art/style/layouts.mjs` (one scale for backdrop, machine and cast, feet on the ground line, art lifted to clear the dialogue box and shrunk when lifting would push the top off the stage; `fitPlate` in `src/story/stage.ts`). A `quado` block there puts Quạ Đồn on his own spot (his feet at `root`); keep it off columns, windows and the art's edge (`tests/stage-rooms.spec.ts`). A `@prop <id>` needs a row in `props` (size and place in the machine frame, optional `landscape` override) and a prop drawing in `art/style/props.mjs`. `scripts/chapters-plugin.ts` writes the backdrops, props and baked sprites a script uses, with their URLs, into that chapter's own chunk (`ChapterScript.stage`, `StoryView.setStage`), so the entry chunk grows with no chapter; `tests/challenge/budget.spec.ts` checks it.
4. `story/meta.json` (title, act, label, year, stamp; from bible §7) drives the timeline, stamps and act-end continue codes. `story/notebook/<id>.json` is the Sổ nguồn card (`status: verified` only with text copied from `research/`); without it `src/notebook.ts` shows a flagged "[Chưa viết]" placeholder. A card's stamp is Cúc Cu's mark art with its label (`src/stamp.ts`): the label wraps to at most 2 lines and shrinks to the `text` box of its own mark in `art/kit/cuccu-rig.json` (`stamp.marks.<id>`); a label with no mark falls back to a plain boxed stamp. `status: draft` in the front matter marks a placeholder chapter.
5. Add the `.size-limit.json` entries, then run `npm test` and `npm run size`. Tests drive `render_game_to_text()` and real pointer events through `tests/support/play.ts` (`chapter1.spec.ts` and `saturnalia.spec.ts` are the models). Tests that need a chapter without a script ask `firstUnwritten()` (`tests/support/script.ts`) and walk to the end of chapter 1 with `walkToChapterEnd`, so none of them names a chapter that is about to be written.
6. Saves hold scene ids (`src/save.ts`); renaming a scene id breaks saved progress, so bump `schemaVersion` and migrate. A save with a newer `schemaVersion` than the build is never read or written: the game plays from memory, the stored save stays as it is, and `#save-newer` asks the player to reload.
7. A name is cut to 24 grapheme clusters, 64 UTF-16 units and 2 combining marks per cluster (`cleanName`); invisible characters go first, NFC runs after them.

# Shell, cards and codes

- On a landscape phone (`orientation: landscape` and height <= 520 px) the dialogue box is at most 150 css px; a longer line scrolls inside it (`.live`). The name-entry dialog (`.ask`) may be 170 px tall there on purpose: its field and button need the room. Expressions: Quạ `doubtful`, Cúc Cu `deflated` (`src/story/types.ts`).

- Directives beyond the basics: `@machine stained|open|stuck [at x,y] [land x,y]`, `@pose <stand|read|sheet|sit> [at x,y] [land x,y]`, `@prop <id>` / `@prop -<id>`, `@turn <teo|cuc-cu|qua-don> <front|three-quarter|side>`, and once per chapter `@timeline`, `@name-card`, `@code`, `@card`. `[khô]` is stripped from a line start (at most 3 per chapter) and is a parse error anywhere else or when misspelled (`[kho]`, or the retired `[đùa]`); `[vì-sao]` is stripped from a line start the same way (misspelled as `[vi-sao]` or `[vi sao]` is a parse error) and marks the line that answers the chapter's "Vì sao?" bible question (rubric R7 item 9, story/bible.md); `{ten}` is the only placeholder and any other `{` or `}` is a parse error. Machine and prop state is rebuilt from the script when a scene is entered (`machineBefore` in `src/flow.ts`). Tèo's pose is the exception: it belongs to the scene, every scene starts `stand` at the plate's default root, and a `@pose` holds until the next one in the same scene. `at`/`land` are the plate coordinates (portrait / landscape) of Tèo's soles, or of the machine's origin; an omitted orientation keeps its default. The poses are one shared set of baked sprites (`teo-<view>-<pose>`, `art/style/teo.mjs`): `read` bends over something laid before him, `sheet` tucks a folded sheet in his belt, `sit` sits on a stool or step the room draws at the same coordinates (ch1 stool, ch2 stool, ch5 step); the hands never hold paper.
- A card screen follows the last scene of every chapter that is not a frame chapter (`intro`, `ending`); a card ending an act also shows the continue code of the next chapter. `?preview=card:<id>` shows a card without playing.
- Continue code `TEO1.<chapter>.<furthest>.n<name base64url>.<FNV checksum>` (`src/code.ts`) holds name, chapter and farthest chapter only; its maximum length follows from `NAME_MAX_UNITS`. Entering a code (`Flow.loadProgress`) sets the current chapter to the code's and the farthest chapter to the maximum of the code, the save in memory and the stored save: a code never lowers it. Reasons `parseCode` returns: empty, length, schema, format, checksum, chapter, beyond, name. Whitespace and every invisible character (`\p{Cf}`, `\p{Default_Ignorable_Code_Point}` such as U+3164, U+FFA0 and the variation selectors, and U+0085) in a pasted code are dropped before parsing; no visible letter is. A finished game writes the chapter field as 25 (`ORDER.length`) and the furthest field as 24; `parseCode` then returns the ending with `finished: true` and `Flow.loadProgress` shows the end screen (the `@code` beat of the last chapter and the Menu on the end screen make such a code), while an older code of chapter 24 still replays the ending from its first scene. While a chapter script loads (`enterChapter`) the mode is `loading` and every screen is hidden; a mini game chunk or script that arrives after `Chơi mới` or a code entry is dropped (`Flow.entering`). `src/storage.ts` falls back to its RAM copy only after the backend failed, so a key removed from `localStorage` stays removed. While it is degraded it still reads and lists what the old backend can give (`keys()` feeds `clearPuzzles`); when a write works again it writes back only the keys this session changed whose backend value is still the one it saw when it first changed them, applies its removals the same way and takes over anything another tab wrote meanwhile; `onRecover` hides the `#storage-warning`.
- Auto-advance waits while a `dialog[open]` is on screen or the tab is hidden and restarts when a dialog closes (`close` event in `src/main.ts`) or the tab shows again. The dialogs, cards and screens scale with the font size setting; `data-reduced-motion` on `<html>` (the player's choice, else the device's) is the only switch for reduced motion in CSS once the script runs.
- Settings live in their own key `teo:v1:settings` (`src/settings.ts`), not in the save, so a save never needs a migration for them. Text speed and volumes are applied through `applySettings` in `src/main.ts`.
- `@name-card` shows the final letter (heading "Thư trả lời gửi {ten}", the answer of the story, signature "Tèo"). Its copy is what Tèo reads aloud in `ending.md` right before the beat, the one place to edit it: `letterOf` (`src/letter.ts`) takes the lines from `Thư trả lời gửi {ten}.` up to `@name-card`, the signer of the heading line signs, and every body line gets a source line `Nguồn: <hosts>`: a claim line (Chắc / Còn tranh cãi / Người ta kể rằng) from the links of the `story/puzzles/ending.json` conclusion pieces of the same status, the opening thesis (the one line without a label) from `conclusion.thesis` in the same file (`source`, `url`, `evidence` like a piece; `slim.ts` keeps only its `url` for the page, `node scripts/puzzles.mjs check` does not read it, `tests/ending.spec.ts` checks it against `research/`). A test keeps the status grouping and the labels of the bank in step. The heading and the body are DOM text (`#namecard-letter`, the sources as links; `textContent`), the `<img>` is an engraved book-page sheet of 1080 x 1350 px (double rules, spaced capitals, the name that shrinks to 12 px and is then squeezed to the sheet width, a signature line) drawn on a canvas after `document.fonts.load` for its text and `document.fonts.ready` (`src/screens.ts`), in EB Garamond only, whose alt is the whole letter. `AbortError` from `navigator.share` is the player cancelling: no message. The timeline prints its legend (Cổ, KT, DG, †) as text and has the caps "Cỗ máy khởi động" and "Hôm nay". Its state is under `story.screen` in `render_game_to_text()`; tests read the PNG bytes through the "Tải ảnh" download.
- `public/og.png` (1200 x 630, no text) is the OG image; its absolute URL in `index.html` assumes the host `teo-co-may-lich-su.pages.dev`.
